# 공동회의 앱 서명키·개인 서명키 보존 정책 (2026-10-25)

## 선장 지시
대화방 이사나 컴퓨터 교체 뒤에도 동일 앱을 업데이트할 수 있어야 한다. 같은 `applicationId`와 동일 인증서의 개인키로 업데이트를 서명한다.

## APK에 넣는 것 / 넣지 않는 것
- **앱 내부 안전한 기록**: 공개 인증서 지문, 패키지명, 버전, 서명 방식, 적용 키 ID, 서명 유효성 검증 결과. `app/src/main/assets/signing-identity.json`에 기록.
- **APK 내부 절대 금지**: 개인키, keystore, P12/PFX/JKS, 암호, 복구 시드. 앱 설치 파일은 사용자에게 배포되므로 키를 넣으면 탈취·위조 APK 제작 가능.
- **별도 보관**: 선장 소유의 접근 제한된 비공개 저장소에 강한 암호로 암호화한 keystore 복구 사본을 만들고, 복구 암호는 별도 오프라인 비밀 관리자에 보관. 별도 복구 위치를 작업대장에 기록하되 비밀값은 문서에 쓰지 않는다.

## 현재 공동회의 시험판 검증
- 앱 패키지 `kr.hanghae.crewmeeting`.
- 기존 v1.0.0 test APK: Android Debug signer certificate SHA-256 `b577038a98e7c5b40e137500068852182e3daa6ea72b7497774d8363884fbd2c`.
- GitHub Actions 사용 키 별칭: `androiddebugkey`; CI 캐시 키 `crew-meeting-independent-pilot-signing-v1`.
- CI에 기존 키 파일 존재 검사, 인증서 SHA-256 고정 검사, 이전 APK 서명 지문 동일성 검사 추가. 키가 없으면 새로운 키를 생성하지 않고 **업데이트 중단**.
- 캐시 보관은 영구 보존을 보장하지 않는다. **개인키 암호화 외부 백업은 아직 확인되지 않았다.** 따라서 서명키 영구 보존 완료라고 보고하면 안 된다.
- 향후 실사용 배포는 강한 암호의 별도 릴리스용 개인키 관리가 필요하다. 기존 시험판을 동일 패키지로 업데이트할 경우 기존 인증서 연속성을 지켜야 한다. 다른 키라면 기존 앱 위에 업데이트 설치 불가할 수 있다.

## 이전·다음 담당자 인계 점검
1. 서명용 원본 keystore를 비공개 위치에서 회수 가능한지 확인. 공개 APK, 코드, 대화 기록에 개인키/암호 입력 금지.
2. 원본 APK의 공개 인증서 SHA-256과 keystore 인증서 SHA-256을 맞춰 읽기 전용 검증.
3. 동일 패키지명, `versionCode` 증가, APK Signature Scheme v2 검증.
4. 임시 파일이나 인증서 불일치 시 APK 배포 차단. 앱 제거/초기화로 해결하지 않음.
5. 선장폰에서 기존 회의 인증 상태·기록 및 업데이트 확인 후 완료로 기록.
